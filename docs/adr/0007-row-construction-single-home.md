# Row construction has one home

What a reps/time/cardio Row carries and its fallback defaults (20 min/8 km h/45 sec/3×10) was hand-rolled in four places — `buildSets` (workout-model.js:109), `insertWarmupRow` (:178), `Workout addSet` (views/Workout.jsx:231), and the `applyPrescription` set-count growth (lib/progression.js:269) — across three directories. Adding a Mode or renaming a field meant four coordinated edits, and the session's progress high-water mark (`Workout.jsx:203,208` + `lib/supersetFlow.js:10` counting `done` alone) counted warm-up rows while every metric, judgement and progression decision excludes them (`isWarmupRow`), a latent Hit/Miss inconsistency in superset flow.

Fix: `lib/workout-model.js` is the one deep Row module behind `makeRow(mode,target,{prev,warmup})` and `ROW_DEFAULTS`/`SETS_DEFAULTS`. `defaultConfig` now reads the same constants, so plan defaults cannot drift; `buildSets` (history-seeded), `insertWarmupRow` (copies preceding warm-up), `Workout addSet` (copies last row), and `progression applyPrescription` (grows work rows from the last work row) all delegate to `makeRow`. The view and the flow adopt work-row accessors — `isWarmupRow` — so warm-up exclusion is one predicate: `supersetFlow hasWork` and `setProgressHighWater` now count `done && !isWarmupRow`, and `Workout.jsx` high-water refs count work sets only. Consequence: a new Mode touches one file and one defaults table, and superset navigation cannot be tricked by ticking a warm-up.
