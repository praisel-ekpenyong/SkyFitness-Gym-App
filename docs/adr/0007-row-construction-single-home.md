# Row construction has one home

Status: Accepted; amended 2026-10 and 2026-11-28 below.

What a reps/time/cardio Row carries and its fallback defaults (20 min/8 km h/45 sec/3×10) was hand-rolled in four places — `buildSets` and `insertWarmupRow` in `lib/workout-model.js`, `addSet` in `views/Workout.jsx`, and the `applyPrescription` set-count growth in `lib/progression.js` — across three directories. Adding a Mode or renaming a field meant four coordinated edits, and the session's progress high-water mark (in `views/Workout.jsx` and `lib/supersetFlow.js`, counting `done` alone) counted warm-up rows while every metric, judgement and progression decision excludes them (`isWarmupRow`), a latent Hit/Miss inconsistency in superset flow.

Fix: `lib/workout-model.js` is the one deep Row module behind `makeRow(mode,target,{prev,warmup})` and `ROW_DEFAULTS`/`SETS_DEFAULTS`. `defaultConfig` now reads the same constants, so plan defaults cannot drift; `buildSets` (history-seeded), `insertWarmupRow` (copies preceding warm-up), `Workout addSet` (copies last row), and `progression applyPrescription` (grows work rows from the last work row) all delegate to `makeRow`. The view and the flow adopt work-row accessors — `isWarmupRow` — so warm-up exclusion is one predicate: `supersetFlow hasWork` and `setProgressHighWater` now count `done && !isWarmupRow`, and `Workout.jsx` high-water refs count work sets only. Consequence: a new Mode touches one file and one defaults table, and superset navigation cannot be tricked by ticking a warm-up.

2026-10 amendment: the work-set judgement now has named readings in `lib/workout-model.js` — `isWorkSet` (phase), `isPerformed` (checked off), `workSets`/`doneWorkSets` (lists) and `hasWorkSet` (trained entry) — and every consumer re-points to them, collapsing the truthy/strict `done` split and deleting `setsDoneActive`, a byte-identical copy of `setsDone`. The same wave gave the per-entry muscle reads one identity precedence: `exerciseFor` (catalogue → embedded exercise → the entry) and `muscleWeightsOf` (own metadata → catalogue → logged snapshot), replacing `loadOf`'s inline fallback, `snapshotWeights`, Stats' local training scan and recovery's catalogue-only lookups, with `lastTrainedByMuscle` (muscles.js) and `lastWorkSetAt` (exercise-progress.js) as the scans' homes. Consequence: a deleted custom exercise keeps counting in fatigue and strength through its logged snapshot, and one precedence — not four — decides what a muscle reading sees.

2026-11-28 amendment: the same module states which Target fields each Mode carries. The exercise config sheet's save and the Plan file export both filter through `pickTargetFields` and keep their own value rules. The list is typed by every key of `Target`, so a new field fails typecheck until it is listed. A planned Target is described in one place, `exLine` in `lib/format.js`, for screens and the printed Plan, with fallbacks from `ROW_DEFAULTS`.
