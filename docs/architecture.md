# Architecture

How Sky works under the hood: the persisted data model, where it lives, and the algorithms that turn history into prescriptions. Vocabulary follows the root [CONTEXT.md](../CONTEXT.md). Decisions and their rationale live in [docs/adr/](adr/).

## The big picture

Sky is a single-page React 19 app with **no backend**. One zustand store (`frontend/src/store/useStore.js`) holds the entire app state as one serializable object `S`; every mutation goes through `update(mut)` (or the named lifecycle actions `beginSession`/`recordWorkingWeight`/`finishSession` behind `lib/active-workout.js`), which deep-clones, applies the mutator, and persists. Views read from `S` and never talk to a server. Pure training logic lives in `frontend/src/lib/` beside its Vitest tests; UI lives in `views/` (pages), `sheets.jsx` (~18 bottom-sheet/dialog flows), and `components/` (custom control set in `ui.jsx`, chart/map/media primitives).

Navigation is a HashRouter over `/home /plan /plan/r/:id /workout /stats /history /library /settings`. There are no context providers: cross-cutting ephemeral state (sheet stack, toasts, rest/work countdowns) lives in a second store, `store/useUI.js`.

## Active-workout lifecycle (`lib/active-workout.js`)

The riskiest writes — building the Active workout, confirming working weight, finishing a Workout with Record/e1RM detection and the heaviest-ever weight cache (`exWeights`) — are the one deep module behind named store actions `beginSession` / `recordWorkingWeight` / `finishSession` and the read seam `bestKnownWeight(S,id)`. The module owns target freezing, `nextPrescription`/`buildSets`/`applyPrescription`, a single monotonic `mergeExWeight` (heavier wins, warm-ups and unticked sets excluded, `topW` included only for the merge, history import reuses the same policy), and the superset-agnostic PR scan. Sheets and Workout are thin callers — see [ADR 0006](adr/0006-active-workout-lifecycle.md).

## Persisted data model (`gym_state_v1`)

The whole state is one JSON object under localStorage key **`gym_state_v1`**. Defaults come from `DEF` in `useStore.js`; saved states are overlaid on a DEF clone via `Object.assign` — a **shallow** merge. Consequence: if a default ever gains a nested field (e.g. inside `reminder`), existing profiles will not pick it up; their old top-level key replaces the whole default object.

Every persist stamps `_ts = Date.now()`. New ids are generated by `uid()` in `lib/format.js` (base36 time + random). Dates are local `YYYY-MM-DD` strings; timestamps are epoch milliseconds.

### Settings / preferences

| Field | Meaning |
|---|---|
| `unit` | `'kg' \| 'lb'`. Switching relabels but never converts logged numbers. |
| `restSec` | Rest timer length in seconds. |
| `sound`, `keepAwake`, `theme`, `accent`, `body`, `gifSize` | Preferences. `body` only affects how the muscle map is drawn. |
| `targetW` | Goal body weight (number or null). |
| `effort` | Which per-set effort scale is logged: `'none' \| 'rir' \| 'rpe'`. Deliberately `null` (not `'none'`) when the profile never chose, so legacy profiles fall back to the replaced `showRir` boolean via `effortOf()` in `lib/history.js`. |
| `reminder` | `{ on, time, tz }` — workout-day reminder. `tz` re-stamped from the device on every boot so travelling stays correct. |

### Collections

- `bodyweight: [{ d, w, t }]` — weigh-ins, sorted by date.
- `routines: [{ id, name, emoji, prog?, ex: [ExCfg] }]` — the emoji-named field actually stores an icon key (`lib/glyphs.js` maps legacy emoji through). `prog` is the routine-default progression policy.
- `week: { dayNum: routineId }` — weekly schedule. Keys are JS `getDay()` numbers (**Sunday = 0**) even though the UI lists days Monday-first.
- `dayPlan: { iso: routineId | 'rest' | '' }` — per-date overrides. `'rest'` forces a rest day; `''` means "back to the weekly schedule". Resolution order in `effectiveRoutineId`: dayPlan override → weekday → week.
- `exWeights: { exerciseId: { w, d } }` — heaviest-ever working weight per exercise ("Best" tags and next-session defaults).
- `customEx: [{ id, n, bp, desc?, custom: true }]` — user-created exercises; registered into the in-memory catalogue index on every persist.
- `workouts: [...]` — completed workouts (below).
- `active` — the in-progress workout, or null.

### Exercise config (`ExCfg`) — plan side

`{ id, sets, sg?, mode?, reps?, sec?, weight?, min?, speed?, bodyweight?, side?, repsMax?, prog?, inc?, repsMin? }`

`sg` is a superset group id: entries sharing an `sg` value must be adjacent (`cleanupSg` enforces; ids look like `sg-{a}-{b}[-n]`). `bodyweight` is set when the exercise disagrees with the catalogue's bodyweight flag. Config sheets write only fields that differ from defaults, keeping shared plan files readable.

### Workout shape

Active workout: `{ id, d, start, routineId | null (freestyle), name, bw, cur, entries: [Entry] }`.
Completed workout (`lib/finish-workout.js::buildCompletedWorkout`): adds `end`, drops empty entries, freezes per-entry `topW`/`target`/`muscleSnapshot`, plus summary fields `unit`, `vol`, `prs` (exercise ids with PRs).

Entry: `{ id, target: ExCfg, sets: [Set], plan?, topW?, asked?, n?, muscleSnapshot? }`
- `plan` — the progression explanation shown for "why this number" (`{ kind, why }`).
- `topW` — confirmed working weight for loaded exercises (prompted once per exercise via `asked`).
- `n` — frozen name for deleted custom exercises; `muscleSnapshot` — frozen muscle map so history survives catalogue changes/deletions.

Set shape varies by logged mode (`modeForSet` in `lib/workout-model.js` resolves explicit `phase`/`mode` → unit token → field presence):
- reps: `{ w, r, done, rir?/rpe? }`
- time: `{ sec, w, done }`
- cardio: `{ min, speed, done }`

Warm-up rows carry `phase: 'warmup'` (legacy rows may have `warmup: true`; `isWarmupRow` accepts both). Optional effort/weight fields are key-**deleted** when cleared, not set to null — cleared ≠ zero, and backups stay minimal. Row shape and fallback defaults (`20 min` / `8 km/h` / `45 sec` / `3×10`) live once in `lib/workout-model.js` as `ROW_DEFAULTS`/`SETS_DEFAULTS` behind `makeRow(mode,target,{prev,warmup})` — see [ADR 0007](adr/0007-row-construction-single-home.md); `buildSets`, `insertWarmupRow`, `Workout addSet` and the `applyPrescription` growth path all delegate there, and the superset `hasWork`/`setProgressHighWater` path counts work sets only (`!isWarmupRow`).

## Persistence protocol

Web build: every `persist()` writes `S` synchronously to `localStorage` (`gym_state_v1`) and mirrors it to IndexedDB (`sky-state` db, `state` store) via `lib/storage.js` on an 800 ms debounce (flushed immediately on `visibilitychange → hidden`). At boot, `pickNewest` compares timestamps (`_ts`) and loads whichever stored snapshot is newer, falling back to empty defaults if neither exists. Settings displays a gentle backup reminder when `backupDue` detects that the last successful JSON export (`S.lastExport`) is older than 14 days.

Mobile (Capacitor) build additionally mirrors state to a native file (`opengym-state.json` in `Directory.Data`, via `lib/mobile.js`):

1. Native writes are debounced 800 ms after each persist.
2. `visibilitychange → hidden` flushes the debounce immediately — backgrounding is often the last event before the OS kills the app.
3. At boot, whichever copy has the newer `_ts` wins; a file copy also beats an empty localStorage. First run after upgrading from a file-less version seeds the mirror.

Why the web mirror exists: iOS Safari can evict WebView localStorage under storage pressure, so dual-write ensures your training log survives even if localStorage is cleared — see [ADR 0004](adr/0004-dual-write-storage.md).

## Training logic

All pure functions over `S`; nothing writes back into finished workouts, so fixing a mistyped set immediately changes the next prescription.

### Effort (`lib/effort.js`)
The internal aggregate unit is RIR (it has a true zero = failure); RPE 8 ≡ RIR 2. A set logged on one scale is never rewritten. Hard set threshold: RIR ≤ `HARD_RIR` (3); averages below `MIN_RATED` (5 rated RIR) render as a dash rather than a misleading number.

### Estimated 1RM (`lib/onerm.js`)
Epley by default (Brzycki/Lombardi available), capped at `REP_CAP` (12) reps — estimates beyond that are refused rather than extrapolated. A real 1-rep set *is* the measurement. Warm-ups and legacy `topW` shortcuts are excluded; reps-mode work rows are authoritative.

### Progression (`lib/progression.js`)
Policy resolution: exercise override → routine default → mode default (`linear` for reps, off otherwise). Miss-streak deloads after `DELOAD_AFTER` misses (linear/double/time: 3, greyskull: 1) at factor 0.9, snapped so the reduction is always at least one loadable step. Bodyweight exercises progress in reps up to `repsMax`, then add sets up to `MAX_BW_SETS` (6), then hold and advise harder variations. Greyskull doubles the increment when the final AMRAP reaches 2× target. Entries predating v1.2.2 have no stored `target`; they are judged against the current plan so old history isn't scored all-miss. Prescriptions carry a translatable `why` template — the UI can always answer "why this number?".

### Recovery (`lib/recovery.js`)
Fatigue per session: intensity-weighted tonnage `load × reps × (load / bestEpley)^1.5` distributed over muscles by snapshot weights (cardio counts minutes × 50 kg proxy). Sessions are normalized against a causal EWMA reference built only from *earlier* sessions, then accumulated with a half-life of `FATIGUE_HALF_LIFE_MS` (36 h) through saturating `1 − e^−v`, scanned over `FATIGUE_SCAN_MS` (30 days). Deleting a workout can therefore never raise fatigue. Strength retention holds at full for `STRENGTH_FULL_MS` (14 days) then decays with a `STRENGTH_HALF_LIFE_MS` (28-day) half-life toward a 0.5 floor. The monotonicity invariant is enforced as a property test by `scripts/fatigue-monotonic-probe.mjs` (`npm run test:fatigue-probe`).

### Muscle mapping (`lib/muscles.js`)
Effective-set weights: target 1.0, synergist/secondary 0.4. Free-text muscle names collapse onto 19 drawable slugs via a curated alias table; customs without metadata fall back to by-bodypart distributions.

## Import / export

- **Backups** (`views/Settings.jsx`): plain JSON of `S`, validated minimally (must contain `workouts` and `routines`), merged onto fresh DEF and swapped in atomically via `replaceState`.
- **Other apps** (`lib/import-csv.js`): one-set-per-row CSV from Strong, Hevy, FitNotes (iOS + Android dialects detected by signature headers), plus Apple Health `export.xml` for weigh-ins. Dates resolve day-first when ambiguous; units convert per row against the profile unit; effort columns follow blank ≠ rated, RIR wins if both present, cap at 10. Exercise matching refuses to guess on ties (the row becomes a custom exercise instead). Extending the curated `ALIAS_EX` table is the sanctioned way to improve match accuracy. Re-importing never duplicates: merge dedupes **by date**, existing days win.
- **Plan share** (`lib/plan-share.js`): self-contained JSON bundles tagged `opengym_plan: 1` (`PLAN_FMT = 1`). Merge guarantees: routines always get fresh ids (never overwrite), customs dedupe by name+bodypart, optional `schedule: true` replaces the whole week. Also renders printable HTML.

## i18n & instructions

Sky ships English only ([ADR 0003](adr/0003-english-only.md)). English strings are still wrapped in `t('literal')` and act as their own keys — `t()` passes them through (substituting `{0}`-style args), so re-introducing a language later remains a one-file change around `lib/i18n-core.js`. The old locale/instruction packs and their key-parity check scripts were deleted with ticket 05; exercise instructions always render from the catalogue's English `st` field via `instrFor()`.

## Build, PWA, mobile shells

- `vite.config.js`: `base: './'` so the build runs from any static path; there are no dev proxies — Sky has no server, and local media is served straight from `public/`; an Umami analytics script is injected only when both `VITE_UMAMI_SRC`/`VITE_UMAMI_ID` are set — plain builds are telemetry-free.
- `public/sw.js`: hand-written runtime service worker. Exercise media (`/media/images/`, `/media/videos/`) cache-first; everything else network-first with cache fallback; final fallback is the cached SPA shell. Rest timer notifications use the Notification API directly.
- Exercise media: fetched out-of-band into gitignored `frontend/public/media/` via `npm run media:fetch` (cross-platform `scripts/fetch-media.mjs`); Vite copies it verbatim into `dist/` when present, and the app falls back to the pinned CDN per asset when not.
- Generated artifacts: `lib/exercises-data.js` (dataset of 1,324 exercises) and `lib/body-paths.js` (muscle-map SVG geometry) are generated/pinned — do not edit. Exercise images/GIFs stream from a pinned jsDelivr commit (`VITE_IMG_BASE`/`VITE_GIF_BASE`); they are licensed media and are never committed.
- Mobile shells (`frontend/android/`, `frontend/ios/`) are stock Capacitor wrappers around `dist/`; `npm run build:mobile` rebuilds with `VITE_MOBILE=1`, pins CDN media bases, then runs `cap sync`.

## Testing

Vitest, run with `npm test` in `frontend/`. Tests sit next to the code they cover. Three DOM strategies coexist: **linkedom** (Modals/Workout tests), **happy-dom** (Stats recovery, Workout.remove, boot smoke), and DOM-free pure tests. The fatigue model's monotonicity invariant has its own standalone property-test harness (see Recovery above).
